# Real-time audio in Rust

<MarkerHighlight>Audio callbacks have a hard deadline.</MarkerHighlight> At
48kHz with a 256-sample buffer, the audio thread gets ~5 milliseconds to
produce the next chunk. Miss that, and the user hears a click, a gap, or a
dropout. The constraint shapes everything.

Rust is a strong fit for this work — once you stop using most of the
standard library. The borrow checker prevents data races at compile time,
but a `Box::new` on the audio path will still kill your latency. The
patterns below are what make it work in practice.

## The setup

A typical mobile audio app has three threads that matter:

1. **JS / UI thread** — receives user input, sends control messages
2. **Native dispatch thread** — translates control messages, runs business
   logic, maintains state
3. **Audio callback thread** — runs in the OS audio subsystem (AAudio on
   Android, CoreAudio on iOS), called with strict timing

The audio callback thread must never block, never allocate, never wait on
a mutex. If the JS thread changes a parameter (volume, FX bypass,
whatever), it has to send that change to the audio thread *without* the
audio thread ever waiting.

That&apos;s the core problem. The lock-free SPSC ring buffer is the
solution.

## Lock-free SPSC via rtrb

A single-producer, single-consumer ring buffer is the simplest lock-free
data structure that works for this. One thread writes; another reads;
neither blocks. The Rust crate `rtrb` (real-time ring buffer) implements
this with the right atomic semantics:

```rust
use rtrb::{Consumer, Producer, RingBuffer};

// Setup (called once, off the audio thread)
let (mut producer, mut consumer): (Producer<ControlMsg>, Consumer<ControlMsg>) =
    RingBuffer::new(256).split();

// JS / dispatch thread — non-blocking push
producer.push(ControlMsg::SetVolume { track: 0, value: 0.8 })
    .expect("ring buffer full");

// Audio callback — non-blocking pop, drain everything queued
while let Ok(msg) = consumer.pop() {
    apply_message(&mut state, msg);
}
```

The audio callback drains the buffer at the top of each block, applies
control changes, then processes audio. No locks, no waits, no allocation.

If the producer side is faster than the consumer drains, the buffer fills
up and `push` returns an error. That&apos;s your signal: either the buffer
is too small or the consumer is dropping frames. Both are caught at
runtime, neither corrupts the audio.

## Allocation-free audio path

The other discipline is harder to enforce: zero heap allocations during
audio callbacks. That means:

- No `Box::new`, no `Vec::new`, no `String::from`
- No `format!()`, no logging (most logger macros allocate)
- No deserialisation of JSON / etc. on the audio thread
- No iterator chains that allocate intermediate `Vec`s
- No async / await (the executor allocates and yields, both bad)

The pattern is: pre-allocate everything during setup, reuse buffers on the
audio thread. A `Vec<f32>` of `samples_per_block` capacity, allocated once
before the audio engine starts, that gets overwritten in place each
callback.

Rust&apos;s ownership model helps here — once you understand how to
write code without `Box`/`Vec`/`String` allocations, the compiler keeps you
honest. The pattern transfers from project to project.

## FFI surface

The audio engine compiles to a static library. The app (React Native, in
the case I&apos;ve been working in) calls into it through an FFI layer.
Two design choices matter:

**1. Keep the FFI surface small.** Every FFI function is a maintenance
cost — both languages have to agree on memory layout, lifetime,
error-handling. I aim for ~10-15 FFI functions that wrap the engine&apos;s
public API; everything else stays internal to the Rust side.

**2. Hand opaque pointers across.** Don&apos;t try to share Rust structs
with C ABIs. Allocate a struct in Rust, return a `*mut OpaqueState`
pointer, and have all subsequent FFI calls pass that pointer back. The
caller never inspects it; the Rust side owns the layout. Cleanup is a
single `drop_state(*mut OpaqueState)` FFI call.

## Cross-platform reality

Android AAudio has different behaviour than iOS CoreAudio. Buffer sizes
that work on one device don&apos;t on another. OEM Android implementations
(Samsung, OnePlus, Xiaomi) all have edge cases. The practical answer:

- Pin a known-good NDK version
- Test on at least three OEM devices, ideally including a budget chip
- Build for arm64 first; armv7 and x86_64 are afterthoughts but need to
  work in case the OEM ships them
- Set up a fallback path: if AAudio rejects your preferred buffer size,
  fall back to the device&apos;s preferred size and warn

The audio engine being correct in isolation doesn&apos;t mean it works on
every device. Real testbed matters more than synthetic benchmarks.

## What this enables

Once the audio path is allocation-free and the control path is lock-free,
you can layer up: multi-track playback, per-track FX chains,
sample-accurate scheduling, MIDI control. The base discipline doesn&apos;t
get harder; you just get more nodes in the graph.

Latency stays sub-20ms on consumer Android hardware. That&apos;s the
threshold below which most users perceive responses as "instant". Above
20ms, they start to feel the lag. Below 20ms, you&apos;re competing with
desktop DAWs on the basic feel.
